## 1. 系统架构

### 1.1 总体结构

**TR（项目说明书 §1.3、§1.4；SRS §2.1）**：系统覆盖用户服务、设备运维、数据存储、决策分析和智能预测，由用户端、PC 管理端、SQLite 数据端、Web 大屏、ML 子系统组成。

```text
ncs_user (Qt Widgets) ─┐
                       ├─ TCP length-frame + JSON ─ ncs_admin/server process
ncs_admin (Qt Widgets) ┘                              │
                                                     ├─ Service
                                                     ├─ Repository
                                                     └─ SQLite charge_platform.db

SQLite aggregates ── export contract ── web/public/data/dashboard.json ── Vue/ECharts
SQLite charging_order ── Python train/predict ── load_prediction ── Admin/Web
```

### 1.2 分层规则

- **TR（NFR-M-02）**：UI 不得出现 SQL。
- **PDD（等价数据访问层）**：项目采用 `UI → Facade/Network → Route → Service → Repository → Database`。SRS 中“SQL 仅存在于 database/service”按职责解释为“SQL 仅存在于专用数据访问层”；本项目的 Repository 即该专用层。SQL 不迁入 Service，以免破坏职责隔离。
- UI 不访问 SQLite、不直接操作 socket、不实现余额、订单、结算规则。
- Route 负责鉴权、字段解析和响应映射，不写 SQL。
- Service 负责业务规则、事务与幂等。
- Repository 负责参数化 SQL 和数据映射。
- Database 负责连接、Schema、migration、WAL、FK 和备份。

### 1.3 可保留的既有资产

TCP framing、JSON request/response、RequestRouter、NetworkServerHost 线程、QStandardPaths、WAL、foreign_keys、MigrationManager 思路、Repository/Service 分层、C1 状态机、条件更新、事务、并发保护、`charge.active` 语义、预约超时思想、Phase4 视觉语言和 Linux Verify 均保留。

## 3. 线程模型

### 3.1 主线程与服务器线程

- **TR（项目说明书 §1.2/§1.6）**：主框架必须为多线程。
- UI 运行在 Qt GUI 主线程。
- `NetworkServer` 运行在 `NetworkServerHost` 管理的专用 `QThread`。
- QTcpServer 在服务器线程内以事件驱动方式管理多个连接；不为每个连接创建阻塞线程。
- SQLite connection 只在创建它的服务器线程使用，不跨线程共享 `QSqlDatabase`。

### 3.2 定时任务

- UI 的 1 秒定时器只刷新展示，不决定订单真相。
- 预约超时以服务端时间为权威；所有订单入口先清理到期预约。
- **PDD**：服务器增加轻量周期清理器，避免长期无人请求时桩一直 Using；惰性清理继续作为兜底。
- 管理端时钟/指标刷新不得阻塞 server 线程。

## 4. TCP 通信设计

### 4.1 保留格式

- 4 字节大端无符号长度 + UTF-8 JSON payload。
- payload 最大 1 MiB。
- Request：`request_id`、`type`、`data`。
- Response：`request_id`、`success`、`code`、`message`、`data`。
- 保留 `protocol_version=1`，建立显式兼容规则。

### 4.2 认证扩展

- **PDD（项目说明书 §2. 数据安全）**：登录成功由服务端生成不可预测 `session_token`。
- 用户 route 与管理员 route 使用不同 token 类型和命名空间。
- 客户端后续请求在 `data.session_token` 携带 token；Service 的 user/admin id 只来自服务端 SessionManager，不信任客户端任意 id。
- token 仅存内存，服务器重启后失效；用户可重新验证码登录，管理员重新密码登录。
- 日志不得记录密码、验证码或完整 token；只允许记录 token 的不可逆短指纹。
- route、字段、错误码与认证要求见 `docs/protocol.md`。

## 5. 数据库设计

### 5.1 通用约束

- **TR（UC-D-01）**：正式表至少包含 `user/admin/station/charger/charging_order/ops_log/load_prediction`；本项目同时实现 `recharge_log`。
- **TR（UC-D-03）**：每连接 `foreign_keys=ON`，数据库保持 WAL；跨表写必须事务。
- **PDD**：正式 Schema 版本从 v6 升级为 v7；fresh DB 只创建正式表和 `schema_version`，不创建 deprecated `charging_record`。v7 补齐 `load_prediction.horizon_hours`，与智能预测展示契约保持一致。
- **PDD**：金额继续以 SQLite `REAL`、单位元存储，以兼容老师字段语义和历史库；所有写入必须经过 `Money::roundYuan` 四舍五入到 2 位，比较使用分值转换，禁止散落浮点判断。
- **TR（BR-09）**：业务时间存储本地时间字符串。
- **PDD**：格式固定为 `yyyy-MM-dd HH:mm:ss.zzz`，不含时区偏移；部署时区固定 `Asia/Shanghai`。协议可另带显示字符串，但数据库只用该格式。

### 5.11 v5→v7 迁移与备份

迁移顺序：

1. 打开连接并验证 WAL/FK；读取 schema_version。
2. 对文件数据库执行 SQLite 在线一致性备份到应用数据目录 `migration-backups/`。备份成功前不得迁移。
3. 只读审计旧 `charging_order`、`charging_record` 的表/列/行数及 active 冲突。
4. 若两个来源存在无法自动裁决的同用户/同桩 active 冲突，停止并输出精确记录，不修改数据。
5. `BEGIN IMMEDIATE`，创建 v6 临时正式表/索引，保留并规范化旧 charging_order 行。
6. v6→v7 补齐 `load_prediction.horizon_hours`，已有预测记录默认按 24 小时窗口兼容。
7. 将 charging_record 按 `legacy_source='charging_record', legacy_id=<id>` 幂等导入；`cost→amount`，station 由 charger 推出，快照由关联表补齐。
8. 相同 legacy key 使用 `INSERT ... ON CONFLICT DO NOTHING`；重复运行不得新增第二份。
9. Repository 切换不是数据库迁移步骤；在同一 Stage gate 内由测试证明新写入只进入 charging_order。
9. 更新 schema_version=6，COMMIT；失败 ROLLBACK。
10. 重新开启并验证 foreign_keys=1，确认 journal_mode=wal，执行 foreign_key_check 和 integrity_check。

旧 `charging_order` 的既有 id/order_no/history 优先保留。无法从旧行推出的快照字段使用关联表当时可得值并在迁移报告标记 `derived during migration`，不得伪装成历史原值。

## 6. 用户认证与授权

### 6.1 手机号验证码

- `user.otp.request(phone)`：服务端校验 11 位手机号，生成 6 位随机数字，保存 5 分钟，60 秒内禁止重复获取；默认响应不回显验证码。课程本地演示可通过 `demo_otp_echo=true` 或 `NCS_DEMO_OTP_ECHO=1` 返回 `display_code` 供 UI 提示。
- `user.login(phone, code)`：服务端校验验证码、有效期和尝试次数；手机号不存在则事务创建默认用户；冻结用户拒绝；成功签发 user session token。
- 默认昵称：`用户` + 手机号后 4 位；余额0、状态1、头像空。
- 正式客户端不调用 username/password route。旧 route 如短期保留，命名 `legacy.user.login` 并仅测试兼容，默认 UI 不展示。

### 6.2 SessionManager

- token 使用加密安全随机源，至少 256 bit。
- server 保存 token→principal(user/admin id)、类型、创建/过期时间。
- 用户 token 不可调用 admin route，admin token 不可替代 user token。
- 注销立即失效；超时返回 `AUTH_SESSION_EXPIRED`。
- 受保护业务从 token 解析 user_id，不接受客户端覆盖。

### 6.3 冻结语义

- 冻结用户不能登录、预约、开始新充电。
- **PDD（解决 BR-07 边界）**：已 Charging 后被冻结，不强制中断；允许查询 active、停止和结算，避免设备/订单永久占用。

## 7. 订单状态机

```text
None ── reserve ──> Reserved(0) ── start ──> Charging(1) ── settle ──> Completed(2)
                       │
                       ├─ cancel ──> Cancelled(3)
                       └─ expire ──> Cancelled(3)
```

- Reserved/Charging 时 charger=Using；Completed/Cancelled 后 charger=Idle，Fault 由管理操作表达。
- 正式 UI 只展示“预约”，不展示直接开始。
- 旧 `charge.start` 无 order id 路径标为 Legacy Compatibility Path；正式用户 UI 不提供该入口，正式回归只以“预约→开始”作为主流程。该兼容分支待跨组兼容窗口结束后由 Owner C 移除，不得作为 UC-U-07 完成证据。
- active 拦截决策：
  - **PDD（解决项目说明书与 SRS 冲突）**：Reserved 直接恢复预约控制页，可开始/取消；Charging 恢复充电控制/结算页；二者都禁止重新选桩。
- **TR（BR-04）**：预约和开始充电均校验可用余额不低于起充金额。
- **PDD（集中配置）**：`charge.min_balance` 默认5.00元，`charge.reservation_minutes` 默认15；由跨平台 QSettings 读取，非法配置回退默认值，业务代码不散落常量。
- 冻结校验与余额校验均在预约/开始事务内执行；冻结后已有 Charging 订单仍可结束结算。

## 8. 计费算法

### 8.1 统一 ChargeCalculator

输入：`start_time`、服务端当前/结束时间、`power_kw`、`price_per_kwh`、`time_scale`、`initial_soc`。

```text
elapsed_real_seconds = max(0, now - start_time)
elapsed_sim_seconds  = elapsed_real_seconds × time_scale
energy_kwh           = power_kw × elapsed_sim_seconds / 3600.0
amount               = round_half_up(energy_kwh × price_per_kwh, 2)
duration_minutes      = floor(elapsed_sim_seconds / 60)
```

- **TR（UC-U-08）**：`charge.time_scale` 默认60；页面每秒刷新。
- UI 与 Service 调用同一无副作用计算组件；最终结算只接受服务端计算结果。
- **PDD（SoC）**：默认 initial_soc=20%；假设演示电池容量60kWh，`soc=min(100, initial_soc + energy_kwh/60×100)`。该算法是演示决定，不宣称老师规定。
- **PDD（配置）**：`charge.initial_soc` 默认20，`charge.battery_capacity_kwh` 默认60；创建订单时快照 time_scale/initial_soc，后续修改配置不改变进行中订单计费。

## 9. 事务与幂等

### 9.1 预约事务

`BEGIN IMMEDIATE → token解析用户 → status/balance/active校验 → charger Idle条件更新Using → INSERT charging_order Reserved → COMMIT`；任一步失败 ROLLBACK。

### 9.2 充值事务

`读取用户余额 → 校验金额 → UPDATE balance → INSERT recharge_log → COMMIT`。

### 9.3 结算事务

1. 由 token 解析用户并读取 Charging 订单。
2. 使用订单快照和 ChargeCalculator 计算最终值。
3. 条件更新 `status=1 → 2`；若影响行数0，读取现状执行幂等响应。
4. charger Using→Idle、total_count+1、total_minutes累加。
5. 计算并更新 user.balance 与 debt_amount/balance_after。
6. COMMIT；任一步失败 ROLLBACK。

**PDD（整型分钟口径）**：`charger.total_minutes` 累加本次模拟时长中已经完整经过的分钟数，即 `duration_seconds / 60`。不足一分钟的尾数不向上放大，订单自身仍保留秒级可重算时长。

### 9.4 幂等策略

- `order.settle` 以 order id + owner + status 条件更新为原子门。
- 已 Completed 的相同 owner 重试返回同一最终小票，不再次扣款/累计。
- 非 owner 永远返回授权错误，不泄露订单状态。
- migration 以 legacy source/id 唯一索引防重复导入。

## 10. 错误处理

统一 `BusinessErrorCode` 分类：

- Protocol：malformed/frame/version/route/parameter。
- Auth：missing/invalid/expired/wrong principal/forbidden。
- User：invalid phone/code/code expired/frozen/not found/nickname/avatar/recharge。
- Order：active exists/not found/not owner/invalid state/expired/already settled。
- Charger：not found/not idle/fault/concurrent conflict。
- Billing：invalid snapshot/calculation/amount。
- Database：open/schema/migration/integrity/transaction。
- Network：disconnected/timeout/write/read。

客户端只展示稳定中文产品文案；技术错误写日志。数据库损坏必须明确提示备份位置和恢复建议，不崩溃、不自动删库。

## 11. 日志设计

- **TR（NFR-M-04）**：日志路径为应用数据目录下 `logs/ncs_YYYYMMDD.log`。
- 格式：`timestamp | level | module | message`。
- server/user/admin 共用 Logger API；线程安全、按日滚动。
- 不记录密码、验证码、头像内容、完整手机号、完整 token。手机号日志脱敏；token 只记短哈希指纹。
- migration/settlement/auth failure 必须有模块化日志；正常每秒 UI 刷新不得刷日志。

## 13. UI 尺寸与交互

## 14. Seed 与可复现性

- 固定 seed 生成：admin 1、station≥5、每站6～12 charger、每站1～2 Fault、快慢充混合。
- 生成约30天 Completed charging_order；start/end、power/time_scale、energy、price、amount、桩/站关联必须自洽。
- seed 只在 fresh DB 的电站目录为空时写入；同一 DB 重复初始化不重复插入，不覆盖已有电站、用户或订单数据。
- load_prediction 可有明确 `demo seed`，但报告继续标 E/ML 未实现。

## 15. 质量 Gate

Stage 2～14 已按本设计完成 Gate。若未来迁移盘点发现无法自动裁决的活动订单冲突或备份失败，仍必须停止并请求人工决定；后续 D/E 功能不得改变本文件定义的正式表和订单事实源，除非经过组长评审。
